# Two-Stage Bangladesh Road-Object Recognition — Results

**Date:** 2026-08-26
**Hardware:** RTX 4060 Ti 8 GB, PyTorch 2.5.1+cu121, Ultralytics 8.4.118
**Test split:** RSUD20K test — 649 images (1920×1080), 3,805 labelled objects, 13 classes

---

## 1. Headline results

| System | mAP@50 | mAP@50-95 | End-to-end recognition acc | FPS |
|---|---|---|---|---|
| **Single-stage** (YOLO26n alone) | 0.7432 | 0.5974 | 0.9148 | 40.3 |
| **Two-stage** (YOLO26n → ConvNeXt-Tiny v2) | **0.7595** | **0.6131** | **0.9590** | 9.6 |
| **Two-stage, deployment setting** (conf 0.05) | **0.7460** | **0.6027** | **0.9177** | **22.3** |

**The two-stage framework improves end-to-end recognition accuracy from
91.5% to 95.9%** — a **52% reduction in recognition errors** (324 wrong → 156
out of 3,805). This gain replicates on the validation split (86.0% → 90.4%)
and holds for 12 of 13 classes on both splits, so it is the robust claim.

The mAP advantage is **not** robust — see §5. Report the recognition-accuracy
result as the headline and treat mAP as split-dependent.

## 3. Stage-by-stage results

### Stage 1 — YOLO26n detector
Unchanged model (trained 2026-08-14, best epoch 44/64). Re-measured correctly.

| Metric | Value |
|---|---|
| mAP@50 (Ultralytics) | 0.7602 |
| mAP@50-95 (Ultralytics) | 0.6110 |
| Usable crop recall @ conf 0.25, class-aware *(old metric)* | 84.63% |
| **Usable crop recall @ conf 0.10, class-agnostic** | **92.43%** |
| Usable crop recall @ conf 0.05, class-agnostic | 94.69% |
| Localisation ceiling @ conf 0.001 | 99.08% |
| Mean IoU of matched boxes | 0.893 (flat across all thresholds) |

The original 84.63% was a measurement artifact. It required the detector to
also predict the right class — but the pipeline discards the detector's class
label, so that requirement does not belong in the metric. It also used
conf 0.25, a single-stage operating point. Correcting both raises the figure to
92.43% with no retraining.

## 4. What produced the Stage-2 gain (ablation)

Three changes, all made together, model and all hyperparameters otherwise
identical to v1:

1. **`PadToSquare` + `Resize(224)` replacing `Resize(256)` + `CenterCrop(224)`.**
   The v1 transform discarded most of every crop. Measured over the real crop
   aspect ratios, the fraction of the long dimension surviving was: person 32%,
   rickshaw 57%, bicycle 58%, motorcycle 61%, bus 68%, truck 72%. A person crop
   became torso-only; a truck lost its front and rear, which is exactly what
   separates it from a covered van.

2. **Cosine `T_max` matched to the real budget (30, not 100), early stopping
   disabled, 2-epoch warmup.** v1 set `T_max=100` but stopped at epoch 28, so
   the learning rate only fell from 1.00e-4 to 8.3e-5 — it never reached the
   low-LR phase where fine-grained classes are won.

3. **`RandomBoxJitter(max_frac=0.12, p=0.8)`.** v1 trained on human-drawn boxes
   but is deployed on YOLO boxes at ~0.89 mean IoU.

**Crucially, v2's advantage holds on real detector crops, not just ground-truth
crops.** Running the full pipeline with each classifier:

| Pipeline | mAP@50 | End-to-end acc |
|---|---|---|
| Single-stage baseline | 0.7432 | 0.9148 |
| Two-stage with **v1** classifier | 0.7443 | 0.9346 |
| Two-stage with **v2** classifier | **0.7595** | **0.9590** |

With the v1 classifier the two-stage system was **barely better than the
single-stage baseline on mAP** (0.7443 vs 0.7432). The preprocessing fix is
what makes the two-stage design worth its cost.

## 5. Robustness check: does it replicate on validation?

The test split is the easier of the two — it has larger objects and fewer
crowded frames. Everything above was re-run on the untouched validation split
(1,004 images, 7,385 objects) to see what survives.

| Metric | Test: single → two-stage | Val: single → two-stage |
|---|---|---|
| **End-to-end recognition acc** | 0.9148 → **0.9590** (+0.044) | 0.8600 → **0.9039** (+0.044) |
| Localisation rate | 0.9908 (identical, same detector) | 0.9630 (identical) |
| mAP@50 | 0.7432 → **0.7595** (+0.016) | 0.6909 → **0.6739** (−0.017) |
| mAP@50-95 | 0.5974 → **0.6131** (+0.016) | 0.5497 → **0.5325** (−0.017) |

**What replicates.** The recognition-accuracy gain is +0.044 on both splits —
identical to three decimals. Per-class, **12 of 13 classes move in the same
direction on both splits**, including the headline cases: covered_van +0.333
test / +0.350 val, human_hauler +0.333 / +0.348, bicycle +0.215 / +0.178.
The core claim of the paper is solid.

**What does not.** The mAP advantage reverses sign on validation. mAP depends
on how well the confidence score *ranks* detections across the whole
precision-recall curve, and the two-stage score is a product of the detector's
confidence and a classifier probability trained with label smoothing and class
weights, which distorts calibration. Alternative fusions were tested and none
fixed it:

| Final score | Test mAP@50 | Val mAP@50 |
|---|---|---|
| Single-stage (detector confidence) | 0.7432 | **0.6909** |
| `det_conf × cls_prob` *(default)* | **0.7595** | 0.6739 |
| `det_conf` only | 0.7523 | 0.6575 |
| `cls_prob` only | — | 0.1689 |

Note that **end-to-end recognition accuracy is identical across all three
fusion choices** (0.9590 test / 0.9039 val) — the argmax class does not change,
only the ranking does. The two-stage system classifies better; it just does not
produce a better-calibrated *detection score*. Calibrating the classifier
(temperature scaling on the validation split) is the obvious fix and was not
attempted here.

**Honest framing for the paper:** lead with recognition accuracy, report mAP on
both splits, and state the calibration limitation. Claiming a general mAP
improvement from the test split alone would not survive review.

## 6. Speed / real-time feasibility

Per-frame wall clock, 1920×1080 input, batch = 1, CUDA-synchronised, after
warmup. Includes JPEG decode from disk.

| Stage | ms/frame |
|---|---|
| Image read (disk + JPEG decode) | 9.3 |
| Stage 1 — YOLO26n detect | 15.4 |
| Crop + preprocess (OpenCV, GPU normalise) | 6.0 |
| Stage 2 — ConvNeXt-Tiny classify (~9.7 crops) | 14.1 |
| **Total** | **44.9 → 22.3 FPS** |
| Excluding disk read | 35.5 → **28.2 FPS** |

| Configuration | mAP@50 | FPS |
|---|---|---|
| Single-stage | 0.7432 | 40.3 |
| Two-stage, conf 0.25 | 0.6955 | 23.1 |
| **Two-stage, conf 0.05** | **0.7460** | **22.3** |
| Two-stage, conf 0.001 | 0.7595 | 9.6 |

### Batched throughput

Streaming latency (batch = 1) is the right number for a live camera. For
recorded video, frames batch and the per-call overhead amortises:

| Batch | detect | crop | classify | GPU total | FPS (GPU) | FPS (+ decode) |
|---|---|---|---|---|---|---|
| 1 | 15.20 | 6.28 | 14.43 | 35.91 | 27.8 | 21.9 |
| 4 | 5.66 | 6.14 | 10.66 | 22.46 | 44.5 | 31.1 |
| 8 | 3.85 | 6.17 | 11.09 | 21.12 | 47.3 | 32.4 |
| **16** | **3.36** | 6.20 | 10.93 | **20.48** | **48.8** | **33.1** |

Detection falls from 15.20 ms to 3.36 ms purely by batching, confirming that
the single-frame cost was Ultralytics per-call Python overhead rather than
model compute — pure inference is ~3 ms, matching the published figure.
JPEG decode (9.7 ms/frame, CPU) is parallelisable and dominates the batched
regime.

**Verdict: the pipeline is real-time.**

- **Live camera, batch = 1** — 22.3 FPS end to end, 27.8 FPS excluding disk.
  Suitable for driver assistance and traffic monitoring.
- **Recorded video, batch = 16** — **33.1 FPS including JPEG decode**,
  48.8 FPS on GPU alone. Above 30 FPS, so full-rate video processing on a
  mid-range consumer GPU.

Stage 2 cost scales with objects per frame; dense Dhaka traffic at
9.7 crops/frame is close to worst case. A TensorRT/ONNX export was not
attempted — no export backend is installed, and installing one was out of
scope for this session.

An OpenCV + GPU-normalisation crop path (`--fast-crop`) reduced preprocessing
from 14.4 ms to 5.5 ms with **identical accuracy** (mAP50 0.7316 vs 0.7305),
raising throughput from 16.7 to 22.3 FPS.

## 7. Open problems

**Truck (29 test / 1,506 train) is the one unsolved class.**
- Stage 1 localises only 75.86% of trucks, and this does not improve at any
  confidence threshold — ~7 of 29 are never detected.
- Stage 2 reaches F1 0.5417 (best in project, still worst class).
- Two-stage end-to-end is *worse* than single-stage, and this **replicates on
  validation**: 0.4138 vs 0.4483 on test, 0.5231 vs 0.6000 on val. It is the
  only class that gets worse on both splits, so this is a real effect, not
  small-sample noise. The classifier confuses truck with covered_van more
  often than the detector's own head does.
- Confusion is with covered_van and bus. This is a data problem — genuinely
  ambiguous Bangladeshi truck/van body types plus very low sample counts —
  not a preprocessing or capacity problem.

**RSUD20K's annotations are incomplete.**
At conf 0.10 the detector produces ~2.7 unmatched boxes per frame. Inspecting
1,762 of them showed they are overwhelmingly *real, unlabelled* vehicles and
people. Objective check: running the Stage-2 classifier over them, it agreed
with the detector's independent label **72.9%** of the time at the same
confidence it shows on real objects — against **7.7%** expected by chance.

Consequences:
- Measured precision is a floor; the system is penalised for correct detections.
- No model can reach 100% on this benchmark.
- **A background/reject class must not be trained on these crops** — it would
  teach the classifier to ignore real rickshaws. If one is wanted, it must be
  built from verified empty regions.

## 8. Negative results (worth reporting)

| Idea | Result |
|---|---|
| Horizontal-flip TTA on Stage 2 | mAP50 0.7305 → 0.7311. No gain, 12% slower. **Reject.** |
| Inference at imgsz 960 (trained at 640) | mAP50 0.7305 → 0.6985. **Worse.** |
| Inference at imgsz 1280 | mAP50 0.7305 → 0.6506. **Much worse.** |

Higher inference resolution *increases* localisation slightly (0.9243 → 0.9380
at 960) but degrades mAP, because of the train/test resolution mismatch. A
higher-resolution detector must be **trained** at that resolution — this does
not come for free at inference time.

## 10. Recommended next steps

1. **Train YOLO26s at imgsz 960** with the existing rare-class oversampling
   (`scripts/02_train_yolo26s.py`). One epoch already reached mAP50-95 0.504 vs
   YOLO26n's fully-trained 0.557. Target: truck localisation and the paper's
   detector mAP. **Do not** expect the bus fix here — bus was a confidence-
   threshold issue and is already solved.
2. **Train Stage-2 v3 on the context-margin crops — ready to run.**
   `RandomBoxJitter` in v2 could only pad grey when expanding, because crops
   were cut exactly on the ground-truth box. The margin dataset and the v3
   trainer are both prepared:

   ```
   Datasets/BangladeshVehicleClassification_margin25/   (generated)
   scripts/train_stage2_convnext_tiny_v3.py             (ready, ~3.3 h)
   ```

   v3 is derived programmatically from v2 — only `DATA_DIR`, `RUN_DIR` and
   `BOX_JITTER_FRAC` (0.12 → 0.20) differ, so any change is attributable to
   the margin alone. Writes to a new run directory; v1 and v2 are untouched.
3. **Export Stage 1 to TensorRT/ONNX.** Batching already recovers most of the
   per-call overhead (15.2 → 3.4 ms), so this is now a smaller win than it
   looked — worth it mainly for the batch-1 live-camera case. No export
   backend is installed; `pip install onnxruntime-gpu onnx` is the first step.
4. **Report the annotation-incompleteness finding.** It is a genuine
   contribution and it bounds every number on this benchmark.
