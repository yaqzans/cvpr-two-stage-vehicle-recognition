Recognition errors fall from 324 to 156 out of 3,805 objects — a 52% reduction. This gain reproduces exactly on the validation split (86.0% → 90.4%, also +4.4 points), so it is the claim to lead with.

Read the mAP column with care

The mAP advantage holds on test but reverses on validation — 0.6909 single-stage against 0.6739 two-stage. Recognition accuracy improves on both. The full analysis is in section 05; claiming a general mAP improvement from the test split alone would not survive review.

02 Where the design actually pays off

Per-class change in end-to-end recognition accuracy, two-stage versus single-stage. Sorted by gain.

The gains concentrate on rare, fine-grained classes a lightweight detector's classification head cannot separate. Common, visually distinctive classes — rickshaw, motorcycle — were already near ceiling and are unchanged.

12 of 13 classes move the same direction on both splits, so this is not a test-set fluke. It is the paper's central claim and the data supports it directly. The magnitudes differ between splits — pickup_truck gains +0.400 on test but +0.068 on val — so quote the direction confidently and the size carefully.

03 Stage 1 was never the bottleneck

No detector was retrained. The improvement came entirely from measuring it correctly.

The original 84.63% crop recall required the detector to also predict the right class. But the pipeline discards the detector's class label — Stage 2 decides. That requirement does not belong in the metric. It also used conf 0.25, a single-stage operating point, when Stage 2 re-checks everything downstream.

Correction to an earlier read

Buses were assumed to be missed because mosaic augmentation fragments large vehicles. The data says otherwise: bus gains nothing from class-agnostic matching at any threshold, but climbs 68.6% → 87.2% purely by lowering confidence. The detector sees buses; it scores them low. That is calibration under class imbalance, not a localisation failure.

04 Stage 2, rebuilt

Same model, same batch size, same learning rate, same seed. Three changes.

  1. Keep the whole object. Resize(256) + CenterCrop(224) was discarding most of every crop — 68% of each person, 28% of each truck. A person crop became torso-only; a truck lost the front and rear, which is exactly what separates it from a covered van. Replaced with pad-to-square then resize.

  2. Let the schedule finish. v1 set T_max=100 but stopped at epoch 28, so the learning rate only fell from 1.0e-4 to 8.3e-5 — it never reached the low-LR phase where fine-grained classes are won. Budget matched to reality, early stopping disabled.

  3. Train on the boxes it will actually get. v1 trained on human-drawn boxes and is deployed on YOLO boxes at ~0.89 mean IoU. Added random per-edge box jitter.

The load-bearing finding

With the v1 classifier, two-stage was barely better than single-stage on mAP — 0.7443 against 0.7432. The preprocessing fix is what makes the two-stage design worth its computational cost. Without it, the thesis does not hold up on mAP.

What holds

The recognition-accuracy gain is +0.044 on both splits — identical to three decimals. Per class, 12 of 13 move the same direction, including the headline cases: covered_van +0.333 test / +0.350 val, human_hauler +0.333 / +0.348, bicycle +0.215 / +0.178. The core claim is solid.

What does not

The mAP advantage reverses sign on validation. mAP depends on how well the confidence score ranks detections across the whole precision-recall curve, and the two-stage score multiplies the detector's confidence by a classifier probability trained with label smoothing and class weights — which distorts calibration. Three fusion strategies were tried; none fixed it:

Final detection scoreTest mAP@50Val mAP@50
Single-stage — detector confidence0.74320.6909

The distinction that matters

End-to-end recognition accuracy is identical across all three fusion choices — 0.9590 test, 0.9039 val. The predicted class never changes; only the ranking does. The two-stage system classifies better but does not produce a better-calibrated detection score.

Temperature-scaling the classifier on the validation split is the obvious fix and was not attempted here. For the write-up: lead with recognition accuracy, report mAP on both splits, and state the calibration limitation plainly.

Verdict — the pipeline is real-time

Live camera, batch 1: 22.3 FPS end to end, 27.8 excluding disk. Suitable for driver assistance and traffic monitoring.

Recorded video, batch 16: 33.1 FPS including JPEG decode, 48.8 on GPU alone — above 30 FPS, so full-rate video on a mid-range consumer GPU.

Detection falls from 15.20 ms to 3.36 ms purely by batching, confirming the single-frame cost was Ultralytics per-call Python overhead rather than model compute — pure inference is ~3 ms, matching the published figure. JPEG decode at 9.7 ms/frame is CPU-side, parallelisable, and dominates the batched regime.

Separately, moving crop preprocessing from PIL to OpenCV with GPU normalisation cut it from 14.4 ms to 5.5 ms at identical accuracy, lifting streaming throughput from 16.7 to 22.3 FPS. Stage 2 scales with objects per frame; dense Dhaka traffic at 9.7 crops/frame is close to worst case.

07 What is still broken

Truck — the one unsolved class

Stage 1 localises only 75.9% of trucks, and that does not improve at any confidence threshold — roughly 7 of 29 are never detected. Stage 2 reaches F1 0.5417, its best ever and still the worst class in the project. End-to-end, two-stage is worse here than single-stage — 0.4138 against 0.4483 on test, and 0.5231 against 0.6000 on val. It is the only class that degrades on both splits, so this is a real effect rather than small-sample noise. Confusion is with covered_van and bus. With 29 test and 1,506 training samples, this is a data problem, not a preprocessing or capacity one.

RSUD20K's annotations are incomplete

At conf 0.10 the detector produces ~2.7 unmatched boxes per frame. Inspecting 1,762 of them showed they are overwhelmingly real, unlabelled vehicles and people. Objective check: the Stage-2 classifier, trained independently, agreed with the detector's label on 72.9% of them at the same confidence it shows on real objects — against 7.7% expected by chance.

Three consequences follow, and all three matter for the write-up:

  • Measured precision is a floor. The system is being penalised for correct detections.
  • No model can reach 100% on this benchmark — the answer key has holes in it.
  • A background/reject class must not be trained on these crops. It would teach the classifier to ignore real rickshaws. If one is wanted, it has to be built from verified empty regions.

10 What to do next

  1. Train YOLO26s at imgsz 960 with the rare-class oversampling already written to disk. One epoch reached mAP50-95 0.504 against YOLO26n's fully-trained 0.557. Target truck localisation and the paper's detector mAP — not bus, which is already solved by the threshold change.

  2. Regenerate crops with a ~25% context margin and retrain Stage 2. Box jitter currently pads grey when it expands outward, because the saved crops carry no surrounding context. ~10 minutes of regeneration.

  3. Export Stage 1 to TensorRT or ONNX to remove ~13 ms of per-call overhead. Likely pushes the pipeline past 30 FPS.

  4. Report the annotation-incompleteness finding. It is a genuine contribution and it bounds every number anyone publishes on this benchmark.
