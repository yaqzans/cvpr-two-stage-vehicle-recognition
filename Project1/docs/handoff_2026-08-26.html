01

The project

Fine-grained Bangladesh road-object recognition using a two-stage deep learning framework. The system takes a road scene and returns a class label and bounding box for every road object, across 13 categories specific to Bangladeshi traffic.

Research question

Does a two-step detect, then classify approach recognise Bangladesh's visually similar local vehicles better than a single all-in-one detector?

The motivation is not generic vehicle detection. It is the confusable local categories — rickshaw versus rickshaw van, auto rickshaw versus micro bus, truck versus covered van — which a single detector must resolve at the same time as it is localising objects in cluttered, dense traffic.

Architecture

road scene 1920 x 1080 | v +---------------------------------+ | STAGE 1 YOLO26n | answers: WHERE, and how sure | 13-class detector, 640 px | +---------------------------------+ | boxes (class label discarded) v crop each box from the full-resolution image | v +---------------------------------+ | STAGE 2 ConvNeXt-Tiny | answers: WHAT | 13-class classifier, 224 px | +---------------------------------+ | v final class per object

The single most important design point

Stage 1's class prediction is discarded. Only its box survives. Stage 2 re-classifies every crop from scratch and makes the final decision.

This has a consequence that shapes every metric in this document: Stage 1 should be judged on localisation, not classification. An early evaluation that required Stage 1's class to match ground truth understated its usable recall by 3–8 points, because it was penalising the detector for mistakes Stage 2 exists to correct.

Classes (13)

person, rickshaw, rickshaw_van, auto_rickshaw, truck, pickup_truck, private_car, motorcycle, bicycle, bus, micro_bus, covered_van, human_hauler.

Note the dataset includes person, so it is strictly a road-object dataset rather than a vehicle-only one. Worth stating explicitly in the paper.

Val is harder than test — this matters when comparing splits

The splits are not equally difficult. Val contains far more small objects: 34.3% of val person boxes fall below the COCO "small" threshold at 640 px against 22.2% in test, and val has zero-to-few tiny buses, trucks and covered vans where test has none at all. Val is also denser (7.4 vs 5.9 objects per image).

Every metric in this document is consistently higher on test than on val. That is a property of the splits, not evidence of improvement.

Dataset B — BangladeshVehicleClassification (classification)

Generated by generate_classification_dataset.py: every ground-truth box is converted from normalised YOLO xywh to pixel xyxy, clamped to the image bounds, cropped from the source image, and written to split/class/ as JPEG quality 95. Boxes smaller than 5 px on either side would have been dropped; none were.

The original RSUD20K split is preserved exactly. Crops from a training image stay in train, and so on. No image contributes crops to more than one split, so there is no leakage between splits — the standard objection to derived crop datasets does not apply here. 130,000 crops total: 118,810 / 7,385 / 3,805.

03

Preprocessing

Stage 1 — detector input

Handled by Ultralytics. Source images are letterboxed from 1920×1080 to 640×640, preserving aspect ratio with grey padding, then normalised. Effective downscale is 3× on the long edge, so a median person box arrives at roughly 20×65 px.

Training augmentation was chosen to stay physically plausible for road scenes — no vertical flips and no rotation, because upside-down vehicles do not occur:

mosaic1.0, disabled for the final 10 epochs (close_mosaic: 10)
horizontal flip0.5
vertical flip / rotation / shear / perspective0.0
translate / scale0.10 / 0.50
HSV hue / saturation / value0.015 / 0.70 / 0.40
random erasing0.4
mixup / cutmix / copy-paste0.0

Stage 2 — classifier input

This is where the single largest correction in the project was made, so both versions are documented.

v1 — the original pipeline

train: RandomResizedCrop(224, scale=(0.70,1.0), ratio=(0.75,1.3333))
       RandomHorizontalFlip(0.5)
       ColorJitter(0.20, 0.20, 0.15, 0.03)
       ToTensor + Normalize(ImageNet)

eval:  Resize(256)        # scales the SHORTER side, preserving aspect
       CenterCrop(224)
       ToTensor + Normalize(ImageNet)

Defect v1 was discarding most of every object

Resize(256) scales the shorter side to 256 and keeps aspect ratio; CenterCrop(224) then takes a square from the middle. On a tight object crop with a non-square aspect ratio, everything outside that square is thrown away.

Measured across the real crop aspect ratios in this dataset, the fraction of the long dimension that survives:

ClassMedian W/HLong dimension kept
person0.3632%
rickshaw0.6557%
bicycle0.6858%
motorcycle0.7161%
truck0.8672%

A person crop of ~60×195 px becomes 256×832, then a 224×224 centre window — torso only, no head, no legs. A truck loses its front and rear, which is exactly what distinguishes it from a covered van. v1's two worst classes were truck (F1 0.478) and covered_van (F1 0.681).

The training transform had the same flaw: RandomResizedCrop with ratio=(0.75,1.3333) cannot satisfy that constraint on a 0.36 aspect-ratio crop, so torchvision silently falls back to a centre crop after 10 failed attempts.

v2 — the corrected pipeline

train: RandomBoxJitter(max_frac=0.12, p=0.8)   # simulate Stage-1 box error
       RandomHorizontalFlip(0.5)
       PadToSquare(fill=(114,114,114))         # pad, never crop
       Resize((224,224))
       ColorJitter(0.20, 0.20, 0.15, 0.03)
       ToTensor + Normalize(ImageNet)

eval:  PadToSquare(fill=(114,114,114))
       Resize((224,224))
       ToTensor + Normalize(ImageNet)

Three changes, and only three, so the comparison isolates them:

  1. PadToSquare instead of CenterCrop. The shorter side is padded with neutral grey to make the crop square, preserving aspect ratio and 100% of the object.
  2. The cosine schedule is allowed to complete. See section 04.
  3. RandomBoxJitter. Each of the four edges is displaced independently by up to 12% of its dimension — positive crops inward (a box too tight), negative expands outward (too loose). This matches the ~0.89 mean IoU that Stage 1 actually delivers, closing a train/serve mismatch: v1 trained on perfect human boxes and was deployed on imperfect detector boxes.

Known limitation of the jitter

The saved crops contain no surrounding context, so an outward jitter pads with grey rather than the real pixels that were there. Regenerating the crop dataset with a ~25% context margin and jittering inside it would make this exact. The script for that exists but has not been run — it produces a different dataset and belongs in a separate experiment.

Why the schedule change matters

v1 set T_max = 100 but early-stopped at epoch 28, so the learning rate only fell from 1.00e-4 to 8.3e-5 — it never reached the low-LR consolidation phase where fine-grained classes are usually won. v2 matches T_max to the real budget and disables early stopping so the schedule always completes, ending at 1.3e-6. Best-checkpoint selection on validation macro F1 still protects against a late regression, so nothing is risked by running to the end.

Both versions select the best checkpoint on validation macro F1, not accuracy — accuracy is dominated by the four largest classes and would hide minority-class collapse. The test set was evaluated exactly once per version, after training.

Evaluation protocol

Metric definitions

  • Usable crop recall — the fraction of ground-truth objects for which Stage 1 produced a box at IoU ≥ 0.5, matched greedily and one-to-one, class-agnostically. This is the correct Stage-1 metric for this architecture because Stage 2 re-labels every crop.
  • End-to-end recognition accuracy — the fraction of all ground-truth objects that the complete pipeline both localises (IoU ≥ 0.5) and labels correctly. Pooled over all objects, not macro-averaged.
  • Class accuracy given localised — of the objects that were localised, the fraction labelled correctly. Isolates Stage 2's contribution from Stage 1's recall.
  • mAP@50 / mAP@50-95 — 101-point interpolated AP, COCO protocol, macro-averaged over the 13 classes.

Evaluator validation

mAP is computed by our own code (06_evaluate_pipeline.py) rather than by Ultralytics, so that the identical evaluator scores both the single-stage and two-stage outputs. It was validated by scoring raw YOLO output: it returns mAP50 0.7432 where Ultralytics reports 0.7602 on the same checkpoint and split — a 2.2% relative difference attributable to letterboxing and NMS handling. Absolute values are therefore not directly comparable to published Ultralytics numbers, but all internal comparisons in this document are consistent.

Detection score

For the two-stage system the detection score is detector_confidence × classifier_probability. Two alternatives were tested and are worse — see section 07.

Timing

Per-frame wall clock at 1920×1080, batch size 1, with CUDA synchronisation around each stage and three warmup iterations. Reported figures are the mean of three consecutive runs on an idle GPU. An earlier measurement pass produced 43.6 and 29.2 FPS for identical configurations because other work was sharing the card; those numbers were discarded.

The largest gains land exactly where the preprocessing defect predicted: bus, truck, covered_van and rickshaw_van — wide or tall objects the centre crop was mutilating. person going 0.9645 → 0.9923 is the cleanest confirmation, since person was the class losing 68% of its pixels.

Overfitting

Both versions overfit. v2 ends at 99.3% train accuracy against 94.7% validation accuracy, and validation macro F1 peaked at epoch 17 of 30. DROP_PATH_RATE and RANDOM_ERASING are wired into the v2 script and default to 0.0; they were left off deliberately so this run isolates the three intended changes. They are the obvious first lever for a v3.

Calibration

Label smoothing and class weighting together leave the classifier's probabilities poorly calibrated. A single temperature fitted on val (real detector crops, never test):

MetricT = 1T = 0.6508

T below 1 means the model was under-confident — right 94.8% of the time while claiming 76.7%. Calibration error improved 11.7× and accuracy is bit-identical, as it must be since a single scalar cannot move an argmax. This is a legitimate standalone result. It did not improve detection mAP — see section 07.

The gain is confidence-dependent — quote the operating point

Two-stage is positive on both splits at both thresholds, but the size of the advantage depends on where the detector's confidence sits: +4.3 / +4.4 at conf 0.001, +2.4 / +1.4 at conf 0.05.

The mechanism is straightforward. A high-confidence detection is one the detector was already sure about, so its own class head is reliable there. Stage 2 earns its keep on the uncertain detections — precisely the ones a higher threshold discards. This is worth stating as a finding: the benefit of a two-stage design scales with how much low-confidence output the detector is permitted to emit.

22.8 FPS is near-real-time, not real-time. On a live 30 FPS feed the pipeline drops roughly one frame in four. Disk read vanishes on a camera feed, lifting it to 28.2 FPS. The two-stage design therefore costs 42% of throughput to buy its accuracy — that trade-off is the project's real engineering claim and is more defensible than any accuracy figure alone.

FPS is nearly flat from conf 0.05 to 0.25 (22.8 → 23.1) because all of a frame's crops go through the classifier in one batched forward pass, while accuracy falls steadily. There is no speed argument for running above conf 0.05.

Retracted The mAP comparison

An earlier analysis claimed two-stage beats single-stage on mAP. That claim is withdrawn. It holds on test (0.7583 vs 0.7432) and reverses on val (0.6746 vs 0.6909). Splitting the change by class support explains why:

Mean ΔAP50 by class support · two-stage minus single-stage
Class groupValTestSign flips?
Well-populated (5 classes, ≥ 250 obj)−0.0079−0.0004no
Small (8 classes, 23–241 obj)−0.0215+0.0221YES
All 13 ( = ΔmAP50)−0.0163+0.0152YES

On the five classes where AP is measured over enough samples to be meaningful, the two systems are indistinguishable. All movement comes from the eight small classes, where it is large and reverses direction between splits — those eight account for 81% of the val gap. An effect that flips sign across splits is sampling noise.

This is also mechanically expected: two-stage never changes a box, only a label, so mAP — which mixes localisation and classification — is structurally the wrong instrument. Report end-to-end recognition accuracy as the headline and do not claim an mAP win.

08

Limitations

1. RSUD20K's annotations are incomplete

At conf 0.10, Stage 1 emits 2.7 boxes per image that match no labelled object. Inspection shows these are overwhelmingly real, unlabelled vehicles — cars, rickshaws, people, an unlabelled pickup truck.

This was verified rather than eyeballed: running Stage 2 over those 1,762 "false positive" crops, it agrees with Stage 1's independent label 72.9% of the time with a median confidence of 0.728 — against a chance agreement of 7.7% for 13 classes, and 93.2% agreement on known-real crops. Two independently trained models converging on the same label at near-normal confidence means the object is there.

Consequences: measured precision is capped below its true value; no model can reach 100% on this benchmark; and a background/reject class must not be trained on these crops, since roughly three quarters of them are real vehicles. This is worth reporting as a finding — it pre-empts the obvious reviewer question about capped precision.

2. Truck is genuinely unsolved

The only class where two-stage is worse than single-stage, on both splits. Stage 1 caps at 0.7586 localisation and stops improving at any confidence; Stage 2 reaches F1 0.5417 with recall 0.4483. With 1,506 training and 29 test objects this is a data problem, not a schedule problem. Options are heavier oversampling, or merging truck / covered_van / pickup_truck into a supercategory resolved by a dedicated head.

3. Small test supports

Six classes have fewer than 250 test objects and three have fewer than 40. Per-class results for truck, covered_van and human_hauler should be reported with their supports visible and interpreted cautiously.

4. Stage 2 is evaluated two ways

Section 06 uses ground-truth crops (standard classifier protocol, 0.9703 accuracy); section 07 uses real detector crops (0.9671 class accuracy given localised). Both are reported. Do not quote the ground-truth-crop number as the pipeline's accuracy.

5. Not yet done

YOLO26s has not been trained — one epoch reached mAP50-95 0.504 against YOLO26n's fully-trained 0.557, suggesting real headroom, but the full run needs ~2 days. Stage-2 v3 on margin crops is scripted but unrun. Neither affects any result above.
